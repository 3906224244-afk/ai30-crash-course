## 一、需求背景

### 1.1 用户痛点

20～30岁大学生和职场新人，在复杂人际关系场景中频繁面临"不知道该怎么回消息"的困境。典型场景：

- **暧昧对象**：说多说少都不知道分寸，怕被认为舔狗，又怕被认为冷淡
- **拒绝社交消费**：同学约出去玩但不想花钱，不知道怎么拒绝才不伤感情
- **导师催论文**：想延长交稿时间，又想让导师舒服接受

### 1.2 为什么是伪需求的反面

- **频率高**：每周遇到2-3次"不知道怎么回"是常态
- **痛感强**：消息弹出即焦虑，有硬性回复截止时间
- **用户已在找方案**：问朋友（不专业）、搜小红书（不精准）、付费连线主播（太片面）、线下社交课（不解急）
- **现有方案全链路都漏**：没有一个产品能即时 + 深度定制 + 高质量地解决这个问题

### 1.3 赛道判断

没有巨头垄断，无大资本进入。通用AI做的是"你问你答"，竞品做的是"模板套用"。Agent多轮追问 + 人设档案 + 知识库策略生成的完整链条，目前市场空白。

---

## 二、产品定位

为20-30岁年轻人提供**定制化人情世故回复策略**的微信AI技能（SKILL）。用户不离开微信聊天界面，AI主动追问补全信息后生成多条不同角度的回复方案。

---

## 三、产品结构

### 3.1 信息架构

```
人情世故顾问
├── 分流页（首页）
│   ├── 急需答案 → 进入咨询流程
│   └── 提前录入 → 进入人设档案
├── 咨询页（核心流程）
│   ├── Split — 场景输入
│   ├── Ask — AI追问（最多4轮）
│   └── Generate — 策略输出（3-5条）
├── 人设档案页
│   └── 4项信息录入（人生阶段/社交痛点/沟通风格/自由备注）
└── 知识库浏览页
    └── 8类社交礼仪规则检索
```

### 3.2 核心业务流程

```
用户输入求助（自由叙述自己的处境）
    ↓
微信AI匹配技能
    ↓
[Split] 判断意图
    ├── 急需答案 → 进入咨询流程
    └── 提前录入 → 建立人设档案 → 等待后续使用
    ↓
[Ask] 用户自由叙述（先让对方把想说的说完）
    ↓  AI消化完整信息 → RAG检索知识库 → 分析信息缺口
    ↓  追问补缺口（最多4道选择题，每题A/B/C + D自由输入）
    ↓  用户回答 → 继续追问 或 信息充足
    ↓
[Generate] 汇总信息 → 生成3-5条不同角度策略（流式输出）
    ↓
输出结果（话术 + 节奏 + 对方反应预判 + 风险提示）
```

**Ask 阶段设计逻辑**：用户带着故事来求助，自然想多说。先让ta把想说的说完（自由叙述），系统在理解全貌的基础上精准追问缺口。这比"用户一句话 → 选择题追问"更自然——不会因为初始信息密度太低导致追问跑偏。

## 四、Agent 调用机制

产品不是简单的"用户问 → AI答"模式，而是**Agent 多阶段自主推理**。每一个 phase 的切换由 Agent 自动判断，用户只需像跟人聊天一样描述自己的情况。

| 阶段 | 触发条件 | Agent 行为 | 决策逻辑 |
|------|----------|-----------|----------|
| **Split** | 用户首次接触，无场景描述 | 判断意图，分流引导 | 硬编码——场景太简单，不需要调 LLM |
| **Ask** | 用户已输入场景（自由叙述） | 消化完整信息 → RAG检索知识库 → 分析缺口 → 生成针对性选择题追问（≤4题） | Agent 自主判断"信息是否足够"：足够则跳到 Generate，不足则继续追问 |
| **Generate** | 信息充足 / 追问达 4 题上限 | 汇总信息 → RAG检索知识库 → 流式生成3-5条不同角度策略 | 每条策略互不重复，对应完全不同的社交博弈姿态 |

Agent 在整个流程中的角色是**连接器 + 决策器**：它决定什么时候问、问什么、什么时候停、什么时候出策略。调用全程用户无感知——用户只在微信 AI 对话框里正常聊天，Agent 在后台自主运行。

**Agent 检索模式**：不做 Function Calling tool-loop（即不让模型自己决定什么时候调工具）。改为 Agent 在调 LLM 之前**自主预检索**——把 situation + answers 拼成查询 → RAG 检索两个知识库 → 将匹配规则注入 prompt → 单次 LLM 调用。好处：减少 API 往返次数，降低延迟，且避免模型在"该不该调工具"上出错。

## 五、知识库构建与持续运营

### 5.1 双知识库架构

| 知识库 | 服务阶段 | 内容 | 规模 | 作用 |
|--------|---------|------|------|------|
| **Ask 库** | 追问阶段 | 场景关键维度 + 追问方向 + 追问雷区 + 高信号信息 | 11条规则（含 compact + embedding） | 帮 Agent 判断"这个场景该追问什么、哪里是信息缺口" |
| **Generate 库** | 策略生成阶段 | 博弈本质 + 策略路径(含话术/节奏/风险) + 绝对避免清单 | 11条规则（含 compact + embedding） | 帮 Agent 生成接地气、可操作的策略 |

### 5.2 构建流程

```
手写11篇种子草稿（8段式模板：元信息→原文→行为反推→场景映射→深刻理解→理解层→Ask→Generate）
    ↓
合并为 seed-rules.json 金标数据库（130KB, 含11个examples + 11条拆解原则 + 扩展benchmarks）
    ↓
convert-seed-to-kb.js 转换为 ask-kb.json + generate-kb.json（每条含implication/tactical_note/compact）
    ↓
build-embeddings.js 预计算 ZhipuAI embedding-3 向量（1024维）→ ask-embeddings.json + generate-embeddings.json
    ↓
用户使用反馈 → 策略效果数据回流 → 持续优化
```

### 5.3 运营节奏

- **种子阶段（已完成）**：11篇金标种子草稿，覆盖11个分析维度（职场晋升/送礼/托人办事/团队合作/两性吸引力/同事博弈/闲谈/信息防御/框架控制/边界设立/认知层次）。金标 seed-rules.json 冻结不改。
- **RAG 阶段（已完成）**：金标数据入 KB（11 ask + 11 generate），ZhipuAI embedding-3（1024维，0.5元/百万tokens），余弦相似度>0.35匹配，关键词降级兜底。KB 规则以 compact 摘要（~300字/条）注入 prompt，体积降90%。
- **自增长阶段（规划中）**：7步知识加工流水线（质量筛选→预估→提取Ask→提取Generate→去重→打分→compact压缩）处理新文章，pending-review 人工审核后入库。用户高频场景和有效策略自动沉淀，形成知识飞轮。

## 六、全局说明

### 6.1 原子接口匹配策略

微信 AI 调用哪个 SKILL，取决于原子接口描述与用户输入场景的匹配程度。`mcp.json` 中的元描述（name、description、触发场景关键词）直接决定匹配率：

- 描述精准覆盖用户可能的表达方式 → 匹配率高 → 被调用概率大
- 描述模糊或过窄 → 用户求助无法匹配 → 流量流失到其他 SKILL

这是与传统小程序获客的本质区别——**不是做 SEO 抢搜索排名，而是写对元描述抢 AI 匹配概率**。后续根据实际调用数据持续优化描述短语，最大化市占率。

### 6.2 返回格式规范

所有接口返回严格遵循微信AI规范：`fact` + `action` + `card` 三段式。

- `fact`：AI读取的上下文信息
- `action`：AI照此执行的展示指令
- `card`：前端渲染的组件数据

### 6.3 原子组件类型

| 组件 | 用途 | 对应Phase |
|------|------|-----------|
| split-card | 双选项分流 | Split |
| question-card | 选择题/自由题 | Ask |
| strategy-list-card | 策略列表（可复制） | Generate |
| knowledge-card | 知识展示 | 知识库 |
| text-card | 兜底文本 | 异常降级 |

### 6.4 异常处理

- LLM调用失败 → 自动降级到硬编码fallback，用户无感
- 追问超过4轮 → 强制进入Generate
- 用户输入无法解析 → text-card兜底提示

## 七、功能性需求

### 7.1 Split — 分流阶段

| 项 | 说明 |
|------|------|
| 触发条件 | 用户首次进入，situation为空 |
| 正常流程 | 展示两个选项：🆘 急需答案 / 📝 提前录入 |
| 选A | 引导用户输入场景描述 → 进入Ask |
| 选B | 跳转人设档案页 |
| 实现方式 | 硬编码（不调LLM） |

### 7.2 Ask — 追问阶段

| 项 | 说明 |
|------|------|
| 触发条件 | 用户已输入场景描述（自由叙述格式） |
| 核心逻辑 | 用户先自由叙述自己的处境 → AI消化完整信息 → RAG检索知识库 → 分析信息缺口 → 精准追问补缺口（最多4道选择题） |
| 题目类型 | 选择题（A/B/C三个定向选项 + D"若都不符可自行输入"）。信息充足时跳过选择题直接进入Generate |
| 设计原则 | **先自由叙述后追问**——用户本就想多说，初始信息密度越高，追问越精准。避免"一句话→选择题"导致追问跑偏 |
| LLM方案 | DeepSeek v4-pro（推理模型），system prompt为ASK_PROMPT |
| 知识注入 | Agent预检索 ask-kb + generate-kb（余弦>0.35），compact摘要注入prompt |
| Fallback | 硬编码5维度追问（relation/personality/goal/history/constraint） |
| 安全上限 | 追问最多4题，达上限强制进入Generate |

### 7.3 Generate — 策略生成阶段

| 项 | 说明 |
|------|------|
| 触发条件 | Ask阶段信息充足，或追问已达4题上限 |
| 核心逻辑 | 汇总场景+追问信息+人设档案 → RAG检索Generate KB → 流式生成3-5条不同角度策略 |
| 策略结构 | angle（角度）+ script（话术）+ rhythm（节奏）+ counterPrediction（对方反应）+ risk（风险提示） |
| 输出方式 | DeepSeek chatStream 流式输出——降低首token延迟，用户感知更快 |
| LLM方案 | DeepSeek v4-pro（推理模型），system prompt为GENERATE_PROMPT |
| Fallback | 硬编码6场景 × 5策略角度（正向/防守/反问/幽默/直球） |
| 展示格式 | 速查表（策略一览）+ 列表详情（含复制按钮） |

### 7.4 人设档案

| 项 | 说明 |
|------|------|
| 录入项 | 人生阶段、常见社交问题、沟通风格偏好、自由备注 |
| 存储 | wx.setStorageSync 本地存储 |
| 使用 | Generate阶段作为策略生成的输入参数 |
| 积累逻辑 | 每次咨询结束后自动更新，无需用户手动维护 |

### 7.5 知识库

| 项 | 说明 |
|------|------|
| 内容 | 8类社交礼仪规则（随份子、敬酒、拒绝、职场、见家长等） |
| 检索 | 关键词搜索 + 分类筛选 |
| 展示 | 卡片式，点击查看详情Modal |
| 后续规划 | 接入RAG向量检索，替换静态知识库 |

## 八、非功能性需求

| 项 | 要求 |
|------|------|
| 响应时间 | LLM调用 < 60s（微信云函数付费上限），流式输出降低用户感知延迟 |

## 十、获客与运营

### 10.1 小红书矩阵 Agent

产品自身的获客不靠投流，靠**内容矩阵**。搭建多个 Agent 在小红书等平台持续输出社交沟通相关内容（如"导师催论文怎么回""拒绝朋友借钱的三种话术"），内容由 Agent 批量生成、人工审核发布。

矩阵的核心逻辑：**内容吸引 → 让用户知道微信 AI 有这个 SKILL → 用户自行去微信里使用。** 产品解决"好不好用"，矩阵解决"找不找得到"。两者是配套关系。

### 10.2 商业模式（简述）

产品对用户免费。策略建议中可自然嵌入关联推荐（如社交课程、关系咨询等），通过 B 端合作变现。不赚用户的钱。

## 十二、技术设计 — 接口与函数（实现参考）

> 本章反映当前已实现的技术架构（2026/07/15版本）。

### 12.1 整体架构

```
微信AI平台（意图识别 + SKILL路由）
        │
        ├── getSocialAdvice（核心Agent）
        │       │
        │       ├── Split  ─── 硬编码分流，不调模型
        │       ├── Ask    ─── [RAG预检索] + [DeepSeek v4-pro] 或 [硬编码fallback]
        │       └── Generate ── [RAG预检索] + [DeepSeek v4-pro chatStream流式] 或 [硬编码fallback]
        │
        └── querySocialRule（独立查询，单步返回）

RAG层：     rag.searchKnowledge(query, kbType) → ZhipuAI embedding-3 余弦相似度 → top-N compact规则
Prompt层：  prompts.ASK_PROMPT / prompts.GENERATE_PROMPT
模型调用层： deepseek.chat() / deepseek.chatStream()（流式）
知识库层：  ask-kb.json(11条+embedding) + generate-kb.json(11条+embedding)
```

### 12.2 云函数接口

#### getSocialAdvice

| 属性 | 内容 |
|------|------|
| **触发** | 微信AI匹配 mcp.json → 路由到本工具 |
| **入参** | `{ situation: string, answers: Array<{question, answer}>, phase: 'auto'\|'split'\|'ask'\|'generate', profile: object }` |
| **出参** | `{ fact: string, action: string, card: object }` — 严格遵循微信AI两段式 |
| **LLM** | DeepSeek v4-pro（推理模型），Ask用4096 tokens，Generate用8192 tokens，流式输出 |
| **降级** | LLM失败 → 自动切硬编码，用户无感知。RAG无结果 → 关键词降级 |

**入参说明**

| 字段 | 类型 | 必填 | 来源 |
|------|------|------|------|
| `situation` | string | ✅ | 用户原话，逐字提取，不得改写 |
| `answers` | Array | ❌ | 对话历史中的问答对，首次传 `[]` |
| `phase` | enum | ✅ | `auto` 让工具自行判断，也可指定 `split`/`ask`/`generate` |
| `profile` | object | ❌ | 通过 storage 接口读取的人设档案，无则传 `{}` |

**出参结构**

| 字段 | 类型 | 说明 |
|------|------|------|
| `fact` | string | AI读取的上下文地基——分析结果 + 当前状态 |
| `action` | string | AI照此执行的展示指令 |
| `card` | object | 前端组件数据。`card.type` 取值：`split` / `question` / `strategy_list` |

#### querySocialRule

| 属性 | 内容 |
|------|------|
| **触发** | 用户询问纯行情/规则，不涉及对具体人的沟通 |
| **入参** | `{ ruleType: string, context?: string }` |
| **出参** | `{ fact, action, card: { type: 'knowledge' } }` |
| **特点** | 单步返回，不产生追问链 |

### 12.4 状态机 — phase 切换逻辑

```
用户首次进入（无situation）
        │
        ▼
    [split] ── 用户选"急需答案" → 输入场景（自由叙述）
        │                          │
        │                          ▼
        │                      [ask] ─── RAG预检索 → LLM分析缺口
        │                          │         │
        │                          │    信息不足 → 返回选择题追问（≤4题）
        │                          │         │
        │                          │    用户回答后再次进入[ask]
        │                          │         │
        │                          │    ┌────┘
        │                          │    │ 信息充足 或 answers≥4
        │                          ▼    ▼
        │                    [generate] → RAG预检索 → 流式生成5条策略 → 结束
        │
   用户选"提前录入" → 跳转人设页（不进入ask/generate）
```

**Ask 阶段内部 Loop**

```
ask(situation, answers=[])
    │
    ├── RAG预检索 ask-kb(5条) + generate-kb(3条)，compact注入prompt
    ├── 调 llmAnalyzeGaps(situation, answers)
    │       ├── needMoreInfo: false → 直接切 generate
    │       ├── needMoreInfo: true  → 返回第N道选择题追问（A/B/C + D自由输入）
    │       └── 异常 → 降级到 hardcoded analyzeGaps()
    │
    ├── 用户回答追问 → ask(situation, [...answers, {question, answer}])
    │
    └── answers.length >= 4 → 强制切 generate（安全上限）
```

### 12.5 Prompt 层

| Prompt | 文件 | 角色 | 核心约束 |
|--------|------|------|---------|
| `ASK_PROMPT` | `prompts.js` | 信息采集专家 | 读知识库→读场景→分析缺口→追问（≤4题选择题+最后自由题）。信息充足时跳过选择题 |
| `GENERATE_PROMPT` | `prompts.js` | 策略生成专家 | 读知识库→深化理解→3-5条不同博弈姿态策略。每条含话术+节奏+对方反应预判+风险 |

两个 prompt 均包含：身份设定、工作流程、示例分析、输出JSON格式、语气要求。

### 12.6 知识库技术规格

| 项目 | 详情 |
|------|------|
| **Ask KB** | 11条规则。每条含：category/subcategory/condition/implication/tactical_note/compact(~300字) |
| **Generate KB** | 11条规则。每条含：category/subcategory/condition/implication/tactical_note/compact(~300字) |
| **Embedding** | ZhipuAI embedding-3，1024维。离线预计算存入 ask-embeddings.json / generate-embeddings.json |
| **检索** | 余弦相似度>0.35返回top-5 Ask + top-3 Generate，compact摘要注入prompt |
| **降级** | 语义检索无结果→关键词匹配兜底 |
| **金标** | seed-rules.json（130KB，11个examples+11条拆解原则+扩展benchmarks），冻结不改 |
